# Розгортання на хостингу (Render)

## Вибір хостингу

Обрано **Render** (безкоштовний тариф web service) — PaaS з підтримкою Node.js і WebSocket. Альтернативи (Heroku, Fly.io) повноцінного безкоштовного рівня не мають.

## Обмеження безкоштовного тарифу Render

| Обмеження | Наслідок для застосунку |
|---|---|
| «Засинання» після 15 хв без запитів; перший запит — до хвилини (холодний старт) | WebSocket-з'єднання розриваються; клієнт мусить перепідключатися (Socket.io робить це автоматично + `events:sync` відновлює пропущені події) |
| Тимчасова файлова система | Завантажені через Multer файли зникають після кожного рестарту/деплою; для постійного зберігання потрібне S3-сховище або платний диск |
| Безкоштовна PostgreSQL діє 30 днів (+14 днів пільговий період) | Для бази на весь семестр краще окремий постачальник (Neon, Supabase тощо) з безстроковим безкоштовним рівнем |
| Один екземпляр (не масштабується) | Redis-адаптер налаштовано, але фактично працює один інстанс; sticky sessions потрібні лише за кількох екземплярів |

## Кроки розгортання

### 1. База даних

- Створіть PostgreSQL на Render (швидкий старт, але 30 днів) **або** у Neon/Supabase (безстроковий безкоштовний рівень — рекомендовано);
- Скопіюйте рядок підключення → це `DATABASE_URL`.

### 2. Створення Web Service

- Repository: `https://github.com/Vovchik148/Web`, гілка `main`;
- **Build Command:** `npm ci && npx prisma generate`
- **Start Command:** `npx prisma migrate deploy && node src/server.js`
- **Health Check Path:** `/health`

> `prisma migrate deploy` (а не `migrate dev`) — команда застосовує готові міграції з репозиторію, не створює нових і не потребує shadow database. `migrate dev` призначений лише для локальної розробки.

### 3. Змінні середовища (Environment)

```
DATABASE_URL=<рядок підключення до БД>
JWT_SECRET=<довгий випадковий рядок>
JWT_EXPIRES_IN=15m
REFRESH_TOKEN_SECRET=<інший довгий випадковий рядок>
REFRESH_TOKEN_EXPIRES_IN=7d
FRONTEND_URL=https://<адреса фронтенду>
APP_URL=https://<адреса сервісу>.onrender.com
NODE_ENV=production
# Redis: без нього застосунок працює (кеш у пам'яті, без черг і адаптера).
# Безкоштовний Redis можна взяти на Upstash/Redis Cloud і вказати URL:
# REDIS_URL=rediss://default:<password>@<host>:6379
```

Секрети не комітяться в репозиторій — задаються лише в панелі Render.

### 4. Застосування міграцій

Перший старт виконує `npx prisma migrate deploy` (у Start Command). Повторний деплой також застосує нові міграції перед запуском сервера. Перевірити стан можна в логах сервісу або тимчасовою командою Shell: `npx prisma migrate status`.

### 5. Перевірка

1. `GET https://<адреса>.onrender.com/health` → `{"status":"ok"}`;
2. `GET /api/health` → перевіряє також підключення до БД;
3. `/api-docs` — Swagger-документація;
4. WebSocket: підключення з токеном (див. [WEBSOCKET_API.md](WEBSOCKET_API.md));
5. Поведінка після «засинання»: зачекайте 15+ хвилин без запитів, потім підключіться — перший запит триватиме до хвилини, після пробудження Socket.io перепідключиться і відновить пропущені події через `events:sync`.

## Sticky sessions (липкі сесії)

Sticky sessions потрібні, коли застосунок працює **за кількох екземплярів**. Причина: Socket.io під час handshake спочатку використовує HTTP long-polling, і наступні polling-запити можуть потрапити на інший екземпляр, який не знає про це з'єднання → клієнт не отримує повідомлень або з'єднання падає.

На безкоштовному тарифі Render працює один екземпляр, тому sticky sessions не налаштовуються. Якщо перейти на платний тариф з автоскейлінгом:

1. Render балансує навантаження по інстансах; для включення sticky sessions у панелі сервісу потрібно звернутися в підтримку Render (параметр не виставляється самостійно через UI) — Render підтримує session affinity за cookie (див. [render.com/docs/scaling](https://render.com/docs/scaling));
2. Альтернатива без sticky sessions: налаштувати Socket.io **лише на WebSocket** (`transports: ['websocket']` на клієнті і сервері) — тоді кожен запит іде тим самим з'єднанням, і балансувальник не перемикає інстанси посеред сесії;
3. Обов'язково з `REDIS_URL`: інакше події, опубліковані на одному екземплярі, не досягнуть клієнтів інших екземплярів (Redis-адаптер уже підтримується кодом).

## Автоматичне масштабування

Безкоштовний тариф Render **не підтримує** автоскейлінг (один інстанс без SLA). Якщо тариф його підтримує (платні плани), налаштування виглядає так:

1. **Render (платні тарифи):** панель сервісу → *Scaling* → задати мінімальну/максимальну кількість інстансів. Render додає інстанси при зростанні CPU/навантаження та прибирає при спаді. Для WebSocket-застосунку обов'язково разом із sticky sessions і Redis-адаптером (див. вище);
2. **Railway (якщо обрано його):** Variables → `REPLICAS` або автоскейлінг у налаштуваннях сервісу;
3. **Fly.io:** `fly scale count <N> --max-per-region <N>` + параметр `min_machines_running` для автомасштабування за навантаженням (`[http_service] min_machines_running` у `fly.toml`);
4. Усі екземпляри мусять вказувати на спільні `DATABASE_URL` та `REDIS_URL`; міграції застосовуються окремим Release Job / разовою командою, а не в Start Command кожного інстансу (щоб уникнути одночасних `migrate deploy`).

## Моніторинг і журналювання

- Логи сервісу: панель Render → *Logs* (stdout/stderr застосунку, включно з `[sql]`, `[queue]`, `[redis]`, `[socket]` рядками);
- Метрики Prometheus: `GET /metrics` — на безкоштовному тарифі Prometheus треба хостити окремо (або скористатися Grafana Cloud з агентом, що опитує `/metrics`);
- Health checks: Render сам опитує Health Check Path і перезапускає сервіс при збої;
- Рекомендовані метрики для алертів: `http_request_duration_seconds`, `ws_connections_active`, `queue_jobs_total{status="failed"}`, `db_query_duration_seconds`.
